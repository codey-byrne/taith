### Shipping

**You own what is ready to land. Verify each PR independently, hand the person the verified run from the root, then keep your hands off the stack.** You never merge and you never arm auto-merge. The person merges.

**Who runs it.** Shipping waits on the person's merges, so the lead starts a loop runner through the **run-loop** skill (`../run-loop/SKILL.md`) with the PRs, bottom to top, in the loop brief. Without hc the lead follows the steps inline under Claude Code's `/loop`. Use the GitHub CLI (`gh`). Never require Graphite (`gt`).

1. **Verify each PR independently before it is called ready.** One verifier per PR, a subagent that did not write the code. It runs the change the way a user would, on the matching surface, with the repo's verification skill or Claude Code's `run` skill, parent against head. It returns `PASS`, `PASS+NOTES`, or `FAIL` with the head SHA it ran. Record each verdict in your report. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Offer only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. A matching patch-id keeps a verdict only after you check that it applies to the new base and dependencies.
4. **Hand over the landing order.** Report the run bottom-up, with each PR's link, verdict and verified head SHA. Tell the person to merge the lowest PR first, and give the guarded command for it: `gh pr merge <pr> --squash --match-head-commit <verified-head>`. The head guard does not guard the base. On GitHub a PR whose base is still its parent's branch merges into that branch, not trunk, so only the bottom PR is ready at any moment.
5. **After the person merges, move the next PR and nothing else.** Read the merged PR back with `gh pr view <pr> --json state,mergedAt,baseRefName,mergeCommit`. A landed PR reads `MERGED` with trunk as its base. Fetch trunk and confirm the merge commit is in its history. Stop the chain if anything contradicts the verified landing. Then retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`). Replay only its own commits onto the merge result, from the old parent tip you recorded before the merge: `git rebase --onto <trunk-tip> <old-parent-tip> <child>`. Never infer that boundary from the parent's new squash commit. Push with a lease on the remote SHA you captured before the rewrite: `git push --force-with-lease=refs/heads/<child>:<captured-sha>`. If the lease refuses the push, fetch and reconcile the concurrent work. Do not refresh the lease and retry. Step 3's patch-id rule decides whether the verdict survives. When its checks pass and its verdict survives, report it as the new bottom, per step 4.
6. **Leave the stack alone between merges.** Step 5's move of the next PR is the only change to a branch or base. Wait on the person's merge with a background command that returns when the bottom PR's state changes, and a long heartbeat as fallback. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything, with `playbooks/babysit.md` in `check` mode.
7. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict, verified head SHA and who produced it, what the person merged and how you confirmed it, what you restacked, and what the next gap needs.
